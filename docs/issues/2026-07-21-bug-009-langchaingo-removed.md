# BUG-009: langchaingo dropped a real answer behind a "thinking" block; removed the dependency entirely

**Found**: 2026-07-21, during the InsideOut rewrite (P4), running the very first real coaching message through the live Anthropic-compatible API once the user supplied `ANTHROPIC_AUTH_TOKEN`.

**Symptom**: every real coaching message failed with `agent: anthropic generate content: no response`, even though the underlying API call succeeded (confirmed by replaying the identical request with `curl`, which returned a normal, well-formed response).

**Root cause**: the configured model (`claude-sonnet-4-6`, an extended-thinking model on this account) returns a `thinking` content block *before* the real `text`/`tool_use` block. The pinned `langchaingo v0.1.14` Anthropic provider maps every response content block to a **separate** `resp.Choices[i]` — it is not one choice per completion candidate the way most providers use the field, it's one choice per content block. Our own `StreamChat` code only ever read `resp.Choices[0]`, which was the empty `thinking` choice; the real text sat, unread, at `resp.Choices[1]`. This is a different bug from the already-known-and-engineered-around "drops parallel tool calls" issue, but the same underlying cause: `langchaingo`'s Anthropic provider was written before extended thinking existed and represents its response shape awkwardly.

**Decision**: rather than patch around a second real bug in an unmaintained dependency (langchaingo's last commit predates this session by months, and it has an open GitHub issue literally titled "is this project dead?"), the user directed dropping it entirely. The Anthropic Messages API is a small, stable, well-documented surface — its streaming format (`message_start` / `content_block_start` / `content_block_delta` / `content_block_stop` / `message_delta` / `message_stop`) was fully reverse-engineered via direct `curl` testing against the live endpoint during this same debugging session, informing a hand-rolled implementation with no framework dependency at all.

**Fix**:
- `internal/agent/anthropic.go` replaces `internal/agent/langchain_anthropic.go`: implements `ChatStreamer` directly over stdlib `net/http`, building the request JSON, parsing the SSE response, and accumulating content blocks by index (multiple `text`/`tool_use` blocks after a `thinking` block are all correctly captured — the exact bug case).
- Removed `github.com/tmc/langchaingo` from `go.mod` entirely (`go mod tidy`).
- Real fixture-based tests (`internal/agent/anthropic_test.go`) use the *actual* SSE payloads captured live from the proxy as test data — including the exact thinking-then-text and thinking-then-text-then-tool_use sequences that broke the old code — so this exact regression can never silently return.
- Tool-result messages are sent back as Anthropic expects: a `user`-role message with a `tool_result` content block (Anthropic has no separate "tool" role — that's an OpenAI convention `langchaingo`'s abstraction had papered over).
- Non-2xx HTTP responses now surface the provider's actual error message (e.g. `model_not_found: Model "..." is not supported...`) instead of langchaingo's generic, unhelpful `no response` for any empty-content case, HTTP error or not.

**Why it matters**: an abstraction library's job is to hide provider wire-format differences — when the library itself gets that wire format wrong (mapping content blocks to "choices"), the abstraction actively works against you, and no amount of application-level engineering-around can fix it without visibility into the library's internals (which is exactly how this bug was found: reading the vendored source, not the docs). For a single-provider integration on an actively-evolving API surface (extended thinking is recent), owning a small, well-tested direct client is lower risk than depending on a library that isn't tracking that evolution.
