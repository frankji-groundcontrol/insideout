# Setup TUI — a guided two-mode install experience in Go (2026-10-07)

Goal: `insideout setup` — a subcommand of the existing CLI binary — is
a friendly interactive front door that takes a beginner (or their
agent, via flags) from a built binary to a working connection:
**remote** (hosted or self-hosted, signed in with password / emailed
code / magic link) or **local** (a PostgreSQL-backed server on this
machine, env configured var-by-var with health probes at each step).
The experience is written in **Go only**: it composes login, migrate,
and probe capabilities the binary already has, adds no second language
to the setup surface, and persists its result in a config file the CLI
natively reads.

> **Decision (2026-10-07, user direction):** standardize the setup
> experience on Go; do not grow the Python side. This supersedes the
> same-day initial sketch of a scripts-side Python front door. The
> bootstrap split below records why some scripts necessarily remain.

## The experience being built

```
$ insideout setup
  ┌ InsideOut setup ───────────────────────────────┐
  │ Where should this machine connect?             │
  │  › Remote service (hosted, or self-hosted)     │
  │    Server on this machine (PostgreSQL)         │
  └────────────────────────────────────────────────┘
```

Remote path: API base field (default = the hosted URL baked into the
binary) → reachability probe (`/api/v1/me` answering 401 = pass) →
sign-in method (password / emailed code / magic link — the existing
`apiclient` flows, driven in-process) → masked token capture → written
to a 0600 config file (no export lines to copy) → offer to merge the
MCP registration JSON.

Local path: Postgres choice (bundled Docker / own URL) → `.env`
written through a Go catalog that preserves comments and permissions
(values never displayed) → `docker compose up -d postgres` → native
pgx reachability probe → in-process migrate → offer to boot the API
(the same binary, no-args mode) and probe it → summary gate.

## Layer split — what stays scripts and why

The Go TUI exists only after `install.sh` has built the binary, and
`install.sh` needs a Go toolchain. So the bare-machine phase —
installing Go, Flutter, Docker per platform — remains the scripts +
install-skill layer (bash; Python there is pre-existing and out of
scope). The split: **scripts bring a machine up to "binaries built";
the Go TUI takes over from there.** This is why the plan does not
retire scripts, not why it adds to them.

## Architecture decisions

- **Subcommand, not a new binary.** `insideout setup` lives in
  `server/cmd/insideout/` (the dual-mode binary: no args = API server,
  subcommands = client verbs). Single-binary friendliness beats the
  few MB the TUI libraries add; the alternative
  (`cmd/insideout-setup`, keeping the server binary lean) is recorded
  and rejected unless the size proves objectionable.
- **TUI framework: bubbletea + huh** (form/wizard model fits: mode
  select, text fields with defaults, masked inputs, spinners on
  probes). Pinned in `go.mod`/`go.sum`; only the setup command's
  packages import it. No other CLI verb changes behavior.
- **Catalog ported to Go, guarded against drift.**
  `internal/setup/catalog` parses `.env.example` with the same
  documented form rules (uncommented = required; commented = default
  in effect), decides secret-vs-not by variable NAME, and computes
  the same statuses (set / default / placeholder / missing / unset);
  `internal/setup/envwrite` writes `.env` the way the Python helpers
  do: comments preserved, only the matching line replaced, 0600
  before an atomic replace, `INSIDEOUT_ENV_FILE` honored. Go tests
  assert those rules directly, including the quote() round-trip. The
  existing Python tooling (`env_catalog.py`, `env.sh`, the CI
  env-suites batteries) is untouched and must stay green —
  consolidation of the two readers is tracked as a follow-up issue,
  not done in this plan.
- **Config persistence lands in slice 1** — going Go made the old
  stopgap (printed export lines) pointless. A 0600 config file in the
  OS config dir holds api_base + token; resolution precedence is
  process env > config file, implemented **once in
  `internal/clientconfig`** — the package the CLI verbs, the MCP
  server (whose `sessionToken()` currently reads the env var
  directly), and setup all import. Failing test first, per the TDD
  contract.
- **Probes are native, not shelled.** DB reachability via pgx ping
  (pgx is already a dependency — `pg_isready` and its argv-privacy
  dance become unnecessary), API and GitHub via `net/http` (401 on
  `/me` = pass). LLM key: shape check by default; a live probe costs
  money, so it is opt-in.
- **In-process migrate and boot.** Local setup runs the existing
  migrate code directly (no `go run` through `dev.sh`) and can offer
  to start the server by re-execing the same binary.
- **Flags parity with `setup.sh`.** `insideout setup --hosted` and
  `--local --postgres bundled|own` mirror the script's agent contract,
  asserted by a test. `setup.sh` stays for the pre-binary path and as
  the agents' fallback; the install skill is updated to prefer
  `insideout setup` when the binary exists.
- **Hidden capture everywhere.** The TUI masks token/code/link input;
  the plain CLI's shared `prompt()` helper currently *echoes every*
  secret it reads (password, code, magic link, reset link, register
  password) — all of those become hidden terminal reads (via
  `x/term`), honoring the shared-stdin-reader lesson of 2026-08-24.

## Execution strategy — workflows and parallelism (binding)

**User direction (2026-10-07): implementation runs through ZCode's
dynamic workflows with maximal parallelism — a serial pass is
explicitly rejected as too slow.** The mechanism is
[ZCode's dynamic-workflow feature](https://github.com/zai-org/ZCode/tree/main/apps/zcode-cli/packages/dynamic-workflow):
the agent writes a workflow script against the facade — `ask` calls
to named actors, fan-out/iteration for parallel work, phase graphs
for ordering, a journal for replay, and a typed artifact returned at
the end. This plan decomposes into exactly that shape: the six slots
below are the workflow's fan-out actors (disjoint packages, one
`ask` each, structured per-actor status `done|partial|blocked` in
the artifact), the join points are the sequential phase after the
fan-out, and the gates run as the gate phase with repair only on
failure. (Prior art in this repo:
`.grok/workflows/finish-cobalt-neo.rhai`, the same
implement→gate→repair→close shape in the older Rhai form.)

**Session note (2026-10-07):** `/workflow` is not invocable from
inside a ZCode session — no such skill is installed and no `zcode`
CLI is on PATH. In-session, the fan-out executes as **parallel
sub-agents** over the same disjoint packages (identical slot table,
status contract, and gates); the alternative dispatch mechanism is
**Orca orchestration** (`orca` installed, runtime verified running
via `orca status --json`: task DAG, `dispatch --inject`,
`worker_done`/gate messages). Either mechanism implements the same
decomposition; the artifact/status contract below is unchanged.

**Prerequisite — serial, once, before any track starts:**

- Slice 0: the engineering-review gate.
- A lone **deps commit**: add bubbletea/huh **and
  `golang.org/x/term`** to `go.mod`/`go.sum`, measure the dual-mode
  binary size before/after, record the numbers in this plan.
  Baseline (go1.26.3, 2026-10-07): **17,827,666 bytes**, `go vet`
  clean, 19 test packages ok. `go.mod` is a shared file; landing deps
  first and alone is what keeps every parallel track conflict-free.

**Parallel phase — six slots, disjoint by construction.** Go package
boundaries are the parallelism boundaries: a worker never edits
another worker's package.

| Slot | Work | Owns (disjoint) | Needs |
| --- | --- | --- | --- |
| A persistence | precedence helper (env > config), 0600 config read/write | `internal/clientconfig*` | deps commit |
| B flow + UI | pure state machine; huh/bubbletea remote branch with non-TTY refusal | `internal/setup/flow*`, `internal/setup/ui*` | deps commit; A via consumer-defined interface only |
| C auth wiring | hidden terminal reads for every secret `prompt()` caller | `cli_auth.go` (apiclient read-only) | deps commit (`x/term`) |
| D catalog + writer | `.env.example` form rules, quote() round-trip, comment-preserving 0600 writer, `INSIDEOUT_ENV_FILE` override | `internal/setup/catalog*`, `internal/setup/envwrite*` | deps commit |
| E probes | pgx ping, API-401 probe, GitHub probe, LLM shape check | `internal/setup/probe*` | none |
| F release pipeline (optional, own gate; deferred until slices 1–3 land) | CI release job + bootstrap one-liner | `.github/workflows/release.yml`, `scripts/bootstrap.sh` | none |

After the deps commit, **all six slots can hold a worker
simultaneously** — that is the maximal-parallelism target; a blocked
slot yields its worker to a live one instead of idling the fleet.

**Join phase (serial by nature — do not parallelize):**

- `cli_setup.go` command wiring where A+B+C join, plus the
  flags-parity test (`cli.go` registry touch: one worker, one commit).
- Local-mode assembly where B+D+E join (slice 2's guided loop).
- The slice gates: live TTY exercise (hosted remote; scratch bundled
  DB), `go vet && go test ./...` green, flags contract green, Python
  env batteries untouched-green, binary-size number recorded.

**Shared-file discipline.** Docs (`installation.md`, root `SKILL.md`,
the install skill, this plan's checklist) are edited by multiple
slots' closures: allowed in parallel only with per-task hunk staging —
never `git add .`, matching the board's standing rule.

**Close phase.** Per the per-slice closure list above; each slot's
structured status lands in this plan's checklist so the board row
stays truthful.

## Non-goals

- API-key auth as a credential type (remote mode is URL + token).
- Retiring or rewriting the existing bash/Python dev tooling in this
  plan — `env.sh`/`dev.sh`/`keys.py` keep working; consolidation is
  the tracked follow-up issue.
- Local mode from outside a repo checkout (migrations, compose file,
  `.env.example` live in the repo).
- Windows.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| TUI libraries bloat the dual-mode server binary | only setup packages import them; binary size measured before/after and recorded; escape hatch: split `cmd/insideout-setup` |
| Catalog drift (Python vs Go readers of `.env.example`) | Go tests assert the documented form rules; Python batteries stay green in CI; follow-up issue owns consolidation |
| Token leak to screen/scrollback | masked capture; 0600 config; values never printed; env-var precedence keeps CI/agent behavior unchanged |
| Agent flows regress | `setup.sh` flags untouched; `insideout setup` flags tested for parity |
| bubbletea testability | flow logic is a pure state machine tested headless; rendering kept thin |
| Offline environments | all probes skip-with-message when network/tools absent |
