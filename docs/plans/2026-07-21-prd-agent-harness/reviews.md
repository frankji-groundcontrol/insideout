Both reviews executed the locally installed gstack skill rubrics
(non-interactive adaptation: per-issue questions became unresolved

## plan-ceo-review

**Verdict**: This is the right thing to build: fabrication is the verified #1 failure mode of PRD agents, the plan attacks it with mechanical gates rather than vibes, and the one-coach-plus-fresh-context-critic architecture is exactly what the evidence supports — no over-investment found, including the production-hardening half, whose every claim I spot-checked against the code and found true. Mode: SELECTIVE EXPANSION — hold the architecture and scope as baseline, with one blocking hole (critic findings have no persisted home, so the plan's most important mechanical gate silently reverts to trusting the model) and a cluster of majors that share a theme: the plan measures its mechanism (citation compliance) but not its outcome (PRD quality, real-user behavior), leaving the 10x question unanswerable post-ship. Recommended cherry-picks E1-E4 (product telemetry, truth-seeking rubric items, outcome eval, gate kill-switch) are each under an hour of CC work and convert 'we shipped the anti-fabrication harness' into 'we can prove it works'. Fix the blocking finding and route the plan to /plan-eng-review; run /plan-design-review before H2's evidence panel is built.

### Findings

1. **[blocking] (confidence 8/10, Section 1: Architecture Review (mechanical gates))** The plan never says where critic findings are persisted, so the critique→finalize gate cannot be validated server-side. Findings are 'structured JSON (parsed, not streamed to the user)' — if they live only in the coach's conversational context, the gate is back to trusting the model's say-so, which directly contradicts design principle 2 ('Mechanical gates over model judgment... validated server-side, not by the model's say-so'). Fact-ledger facts have a specified home (agent_conversations.meta); findings have none, and neither does the per-finding open/resolved/overridden state the gate must query.
   - Plan quote: “`critique → finalize`: at least one critic pass completed (see 4.4) and no open `blocking` findings, or the user has explicitly overridden”
   - Recommendation: Persist critic findings in the same meta blob as the ledger (e.g. meta.findings with id/severity/status), updated by the relay stage's decision handling, and have the gate query that. Zero new infra, one paragraph in §4.4, and it keeps the gate honest. Tradeoff: meta grows and the relay stage needs a resolve-finding write path. Do-nothing is not viable here — without it the plan's central 'mechanical gates' claim is false at the one gate that matters most.
2. **[major] (confidence 8/10, Section 6: Test Review (outcome measurement))** The eval measures compliance with the mechanism (every sentence cites a fact or is tagged), not the outcome (a good PRD). The research digest's own strongest product finding is that 'template-complete-but-vacuous is the dominant modern anti-pattern' — Aakash Gupta scored a fully-structured PRD 2/10. A coach can pass this eval perfectly while producing citation-decorated filler: cite fact f1 for every sentence and still write lazy metrics and generic requirements. The plan encodes substance checks in the critic rubric but never evals whether the end-to-end output is actually better than the current harness.
   - Plan quote: “Eval (new, small): 3 scripted fixture conversations replayed through the harness; assert zero PRD sentences lacking a fact citation or `[ASSUMPTION]` tag — the fabrication metric this whole plan exists for.”
   - Recommendation: Add a second eval axis to §6: run the same 3 fixtures through the old harness and the new one, and grade both with a decomposed binary checklist (CheckEval pattern already in research.md — named narrow segment? measurable objectives with baselines? current-alternative named? requirements problem-phrased?). ~1 extra hour of work, and it's the only thing that tells you the whole plan paid off. Do-nothing option: ship with the fabrication metric alone and accept you're measuring the seatbelt, not the crash rate — defensible for v1, but say so explicitly.
3. **[major] (confidence 7/10, Section 6: Test Review (critic precision))** The plan defers the critic-model question to 'a small eval' but no critic-precision eval exists anywhere in Delivery (§6). This matters more than the model choice: the research digest's Reflexion finding shows a noisy evaluator pushes output BELOW the no-critic baseline (0.52 vs 0.60), and the MAD finding shows a naively adversarial critic corrupts good drafts. The verification gate (quote must be a PRD substring) checks findings are grounded, not that they are correct or worth surfacing — a critic that floods the relay stage with plausible-but-wrong 'blocking' findings makes the coaching experience worse, and the plan has no way to detect it.
   - Plan quote: “Should the critic run on the same model as the coach or a cheaper one? (Plan assumes same model; a cheaper critic halves cost but weakens the rubric check. Needs a small eval to decide.)”
   - Recommendation: Add a small critic-precision fixture to the eval: 2-3 PRDs with planted known defects plus known-good sections; measure recall on planted defects and false-positive rate on good sections. This also answers open question 1 for free (run it on both models). Tradeoff: fixture authoring effort (~half a day human / ~30 min CC). Do-nothing: the bounded 2 rounds and human-in-the-loop relay limit the damage, so shipping without it is survivable — but you'll be tuning the critic blind.
4. **[major] (confidence 7/10, Section 2: Error & Rescue Map)** The critic is an LLM call that must return parseable JSON, and the plan's own error taxonomy (§5.2) covers provider failures but not this output-shape failure: malformed JSON, empty findings array vs refusal, truncation at max_tokens mid-array. The skill rubric names this class explicitly for LLM calls (malformed / empty / hallucinated-invalid JSON / refusal are distinct failure modes). Unspecified: does a parse failure retry, count against the 2-round bound, trip the circuit breaker, or silently fall through to the degradation ladder's single-context fallback?
   - Plan quote: “Output is structured JSON (parsed, not streamed to the user): findings with {section, severity: blocking|major|minor, quote, issue, suggestion}”
   - Recommendation: Add one row-group to the §5.2 table for critic-output failures: one re-prompt retry with the parse error appended; on second failure, degrade to the already-designed single-context critique with the same visible notice as semaphore contention, never counting as a circuit failure (it's an output-quality problem, not provider health). Reuses the degradation ladder you already built — a few lines of spec. Do-nothing risks a silent gate deadlock: no completed critic pass means critique→finalize can never mechanically pass.
5. **[major] (confidence 7/10, Section 1: Architecture Review (turn lifecycle))** A legitimate turn can exceed 10 minutes: the idle-stream watchdog allows 90s silences ('thinking pauses are long'), a critique-entry turn chains the coach call plus up to 2 critic rounds, and §5.2 adds retries with backoff. Nothing in the plan says ai_runs.updated_at is heartbeated during a live turn — if it's only written at creation and terminal state, the reaper marks an actively-streaming run 'failed' while the handler later marks it succeeded, producing contradictory terminal states and (worse) reaping healthy long turns exactly when the product is doing its most valuable work.
   - Plan quote: “Stale-run reaper: on startup and every 5 min, `UPDATE ai_runs SET status='failed', error_message='reaped: stale' WHERE status IN ('pending','running') AND updated_at < now() - interval '10 minutes'`”
   - Recommendation: Specify a heartbeat: touch updated_at when each provider call starts (coach, tool-loop iterations, critic rounds) — one UPDATE per call, piggybacking on the telemetry write H4 already adds. Keep the 10-minute window. Alternative (smaller but blunter): raise the window to 30 min and accept slower lockout recovery. Do-nothing is wrong: the reaper exists to fix rate-limiter lockouts, and a false-positive reap recreates the exact 'contradictory run state' class it was built to kill.
6. **[major] (confidence 8/10, Section 8: Observability & Debuggability Review)** All planned telemetry is infrastructure-shaped (tokens, latency, error class). None of it tells you whether the flagship coaching mechanics work in production: facts recorded per conversation, gate-denial counts, how often users pull the 'just draft it' escape hatch, [ASSUMPTION] density in finalized PRDs, critic findings accepted vs 'keep as is'. If 80% of users escape-hatch past clarify, the fact ledger is theater and you would never know — the offline eval (3 fixtures) can't catch real-user behavior. For a CEO lens this is the difference between 'we shipped the feature' and 'the feature works'.
   - Plan quote: “Telemetry: actually call `InsertAIRunEvent` (dead today) per provider call: model, input/output tokens (from `message_delta.usage`), latency, error class, and whether it was a coach or critic call.”
   - Recommendation: Extend the H4 event write with a handful of product events (fact_recorded, gate_denied, gate_overridden, critic_finding_{accepted,rejected}, prd_finalized with assumption_count) — the ai_run_events table with its event_type column already fits, so this is ~an hour of CC work riding on wiring you're doing anyway. Tradeoff: a little event-taxonomy bikeshedding now. Do-nothing means the open questions (question fatigue real? lens cap right? critic worth its cost?) stay permanently unanswerable.
7. **[major] (confidence 7/10, Step 0C: Dream State Mapping (truth-seeking content))** The plan quotes 'top 3 reasons this fails' as a mechanical property of good PRDs (§2.2) but never encodes it: the clarify gate requires problem/segment/alternative/whynow facts, the draft gate requires 8 non-empty sections, and the critic rubric is 'the Amazon PR/FAQ 7 reviewer questions + Cagan checks' — the 7 reviewer questions do not include the assumptions-that-must-be-true or top-3-failure-reasons FAQs (those are separate sections in the Working Backwards source), and a non-empty 'risks' section is not a pre-mortem. The research digest calls this the truth-seeking core ('should demonstrate that the authors aren't looking through rose-colored glasses'); the harness as designed can finalize a PRD whose risks section is confident filler.
   - Plan quote: “explicit assumptions with validated/unvalidated tags, "top 3 reasons this fails" — truth-seeking, not selling”
   - Recommendation: Cheapest complete fix: add two binary items to the critic rubric ('does risks contain ≥3 concrete this-fails-because scenarios elicited from the user, not generated?', 'is every [ASSUMPTION] tagged validated/unvalidated?') and one finalize-report line counting them — no new stage, no new tool. Bigger option (defer to TODOS): a pre-mortem micro-stage before finalize per the Doshi pattern. Do-nothing keeps v1 smaller but ships a coach that structurally prevents fabricated facts while still permitting fabricated optimism — the second-order failure mode the research warns about.
8. **[major] (confidence 6/10, Section 3: Security & Threat Model)** The migration's unique index is global (`CREATE UNIQUE INDEX ON insideout.ai_runs (idempotency_key) WHERE idempotency_key IS NOT NULL`), and the plan doesn't scope the duplicate-lookup. Implemented naively, user B replaying a key that collides with user A's run either gets a 500 from the unique violation or — worse — 'returns the original run's terminal state', leaking another user's run status and error_message. Client-generated UUIDs make accidental collision negligible, but the lookup is an authorization boundary and the plan is silent on it.
   - Plan quote: “Idempotency: wire the existing `idempotency_key` column: the client sends a per-turn UUID; a duplicate POST (retry after network blip) returns the original run's terminal state instead of double-running.”
   - Recommendation: One sentence in §5.3: the duplicate lookup is scoped to (user_id, conversation_id, idempotency_key); a key that exists under a different user/conversation is treated as a fresh run with a fresh key (or 409s), never returned across owners. Optionally note the index should become composite in a future migration. Near-zero cost; this is exactly the kind of line an implementer needs decided now. Do-nothing gambles that the implementer scopes it correctly by instinct — cheap insurance against an IDOR-shaped bug.
9. **[minor] (confidence 7/10, Step 0C: Dream State Mapping (persistent context))** The research digest names persistent cross-session product context as 'the single most-cited differentiator vs raw ChatGPT' (Productboard, ChatPRD's 'projects with saved knowledge' as the retention hook), yet the ledger is conversation-scoped and workspace-level memory appears nowhere — not in scope, and notably not in §8 NOT-in-scope either. For InsideOut's actual users (workshop teams iterating on several PRDs about one product), re-attesting the same segment/alternative facts every conversation is the top predicted friction, and the ledger schema (kind/text/quote/status) is already the right shape to lift to workspace scope later.
   - Plan quote: “A conversation-scoped, structured list of user-attested facts, stored in `agent_conversations.meta`”
   - Recommendation: Selective-expansion candidate, not a v1 requirement: add one line to §8 NOT-in-scope ('workspace-scoped fact memory — ledger schema is scope-agnostic; lift to workspaces.meta when multi-PRD usage appears') so the omission is a decision, not a blind spot. Pulling it into v1 would add cross-conversation invalidation complexity that isn't worth it before real usage. Do-nothing (not even naming it) violates the plan's own 'everything deferred must be written down' discipline.
10. **[minor] (confidence 7/10, Section 11: Design & UX Review)** The evidence panel is the user-facing embodiment of the plan's entire trust story, and it gets one bullet plus a Delivery-table cell ('frontend evidence panel'). No states are designed: empty state before the first fact (the panel's most common state), attested vs assumed vs needs-validation rendering, how [ASSUMPTION] items look inside the PRD text, what the user sees during a `queued` wait or after an `[interrupted]` partial turn. A plan this rigorous about server states leaving all UI states implicit is exactly the 'AI slop risk / engineer-designed panel' the rubric flags.
   - Plan quote: “SSE: new `fact_recorded` event so the UI can show a growing evidence panel; the user sees exactly what the coach thinks it knows”
   - Recommendation: Add a half-page interaction-state table (panel × empty/loading/streaming/error; PRD text × assumption/open-question rendering) to H2's scope, and run /plan-design-review before implementing H2. Small cost, and it protects the feature whose felt quality decides whether users trust the coach at all. Do-nothing: acceptable if you treat H2's frontend as a spike to be design-reviewed after — but decide that explicitly.
11. **[minor] (confidence 7/10, Section 9: Deployment & Rollout Review)** Stage gates and lints change core conversational UX, and the plan's only rollback is git revert. A miscalibrated 'everyone' deny-list or an over-strict quote-verification threshold (risk §7 admits false-negatives) degrades every conversation until a redeploy; there is no kill switch, and the phases table has no flagging story despite the gates being the highest-behavior-risk change in the plan.
   - Plan quote: “Segment text failing an "everyone" lint (a short deny-list check) blocks with a targeted error the model relays as a question.”
   - Recommendation: One env var (`AI_GATES_ENFORCE=true|warn|off`) checked in tools.go: 'warn' logs the would-be denial (feeding the gate-denial telemetry above) without blocking — which is also your safest H2 rollout mode for the first week. ~10 lines. Do-nothing is defensible for a single-instance workshop deployment where redeploys are minutes, but 'warn' mode doubles as free calibration data, which tips it to worth doing.
12. **[minor] (confidence 6/10, Section 4: Data Flow & Interaction Edge Cases)** A plain buffered-channel semaphore has no notion of queue position — Go channel semantics give you blocked-or-acquired, not an ordered wait list, so `position: n` cannot be computed from the primitive the plan names. Either the design silently grows a real FIFO queue (more machinery than §5.1's stated primitive) or the event ships with a fabricated/approximate position.
   - Plan quote: “during the wait the handler emits SSE `queued` events ({"position": n}) so the user sees why nothing streams”
   - Recommendation: Drop the position number: emit `queued` as a heartbeat ({"waiting": true}, repeated) — the user's actual need is 'the system knows about me and I haven't been dropped', not an integer. If a position is truly wanted later, an atomic counter of waiters gets you an approximate one for ~5 lines. Do-nothing (keep the position spec) forces the implementer to invent an ordered queue the plan explicitly avoided.
13. **[minor] (confidence 6/10, Step 0A: Premise Challenge (workshop-team fit))** The entire coaching loop is single-user (conversations are owner-scoped in coach.go), but InsideOut's users are workshop teams, and the research digest's PRD-process findings are heavily multi-stakeholder (silent-read reviews, cross-functional critique, the funnel). Teammates today can edit PRD sections but cannot see the evidence panel, contribute attested facts, or participate in the critique relay. Fine for v1 — but like workspace memory, this boundary is undeclared: §8 NOT-in-scope doesn't mention team participation at all, so the most product-shaped scope question in the plan was never consciously decided.
   - Plan quote: “critique: becomes a thin relay stage — it presents critic findings (4.4) one at a time, gstack-style: one issue per turn, an opinionated recommendation, a "keep as is" option”
   - Recommendation: Add 'multi-member coaching / shared critique sessions' to §8 NOT-in-scope with one line of rationale (single-owner conversations; teammates collaborate via PRD edits + the existing review flow). Zero build cost — this is a documentation-of-decision finding. Do-nothing leaves reviewers and future contributors re-deriving whether the omission was intentional.

## plan-eng-review

**Verdict**: Strong plan: the problem statement is code-verified (I re-verified every §1 claim against the repo and all but one hold), the research genuinely drives the design, and the reuse discipline is exemplary — meta jsonb, the dormant idempotency column, ai_run_events, and the existing breaker are all reused rather than rebuilt. The findings are contract-consistency defects, not architectural ones: one factually wrong causal claim (reaper does not fix rate-limit lockouts — the limiter counts by created_at regardless of status), a reaper that can kill healthy long turns, an SSE-vs-503 contradiction in the semaphore contract, a load-dependent finalize deadlock between the degradation ladder and the stage gate, and an untouched maxToolIterations=6 budget that the new fact tools will exhaust. Per the rubric this lands as issues_open / FULL_REVIEW with scope accepted (complexity smell triggered but justified; one H4 slim-down proposed): fix the ~6 major findings on paper — each is a one-to-three-sentence plan edit — before implementation begins, and this is ready to build.

### Findings

1. **[major] (confidence 9/10, Architecture review)** The reaper's rate-limit rationale is factually wrong against the actual SQL. ai_check_rate_limit (20260720135755_ai_ops.sql) counts ALL ai_runs in the sliding window with no status filter — 'Failed runs count too (anti-abuse)' is in the migration comment, and the count query is `WHERE user_id = p_user_id AND created_at > now() - interval '1 minute'`. Marking stale rows 'failed' changes nothing for the limiter; the lockout exists (and expires) purely via created_at, reaper or not. The reaper is still worth building (data hygiene, accurate telemetry, UI run status), but the plan's §1 claim 'the rate limiter counts them — a crashy hour can lock a user out' misattributes the cause and §5.3 claims a fix that does not occur.
   - Plan quote: “Fixes crash-abandoned runs and the rate-limiter lockout they cause.”
   - Recommendation: Correct the plan text: keep the reaper, drop the rate-limiter-lockout claim, and if crash-lockout is a real concern, decide separately whether reaped runs should be excluded from the limiter count (a one-line status filter in the SQL function — but that weakens anti-abuse, which the migration comment says is deliberate). Do-nothing option: ship the reaper as-is and accept the plan doc contains one wrong causal claim — cheap, but it will mislead the implementer into thinking lockouts are fixed when they are not.
2. **[major] (confidence 8/10, Architecture review)** The reaper can kill live runs. ai_runs.updated_at is set at creation and only touched again at terminal states (MarkAIRunSucceeded/MarkAIRunFailed); there is no heartbeat during streaming. A legitimate long turn — up to 6 tool iterations (coach.go: `const maxToolIterations = 6`), each provider call allowed 90s of idle silence per the plan's own AI_STREAM_IDLE_TIMEOUT, plus retries and (H3) a critic pass in the same request — can plausibly exceed 10 minutes. The reaper would then mark a live run 'failed' mid-stream, and the handler's later MarkAIRunSucceeded races against/overwrites the reaped state.
   - Plan quote: “UPDATE ai_runs SET status='failed', error_message='reaped: stale' WHERE status IN ('pending','running') AND updated_at < now() - interval '10 minutes'”
   - Recommendation: Add a cheap heartbeat: bump ai_runs.updated_at once per provider call (start of each runLoop iteration) — one UPDATE per call, and 10 minutes then genuinely means 'no provider activity for 10 min'. Alternative: raise the window to comfortably exceed worst-case turn time (e.g., 30 min), zero code but slower recovery of crashed runs. Do-nothing is not safe here: as written this is a new production failure mode (healthy long turns marked failed) introduced by the fix.
3. **[major] (confidence 8/10, Architecture review)** Contract contradiction in the semaphore design. The semaphore wraps 'every provider call', and provider calls happen inside runLoop — after sse.messageStart() has already sent SSE headers (coach.go:117). The plan simultaneously says the handler 'emits SSE queued events' during the wait (stream open) and returns a '503 CIRCUIT_OPEN-shaped response' on timeout (impossible once headers are sent). The 'existing frontend countdown handling' (useCoachStream.ts isRateLimited/retryCountdown) handles pre-stream JSON 429/503, not an in-stream SSE error. Additionally, mid-turn tool-loop iterations would each re-acquire the semaphore, so a turn can stall between a tool result and the continuation call — plan doesn't say whether acquisition is per-call or per-turn.
   - Plan quote: “on timeout: 503 `CIRCUIT_OPEN`-shaped response (reuses the existing frontend countdown handling)”
   - Recommendation: Pick one point in the lifecycle: acquire the semaphore once per turn, before the SSE stream opens — pre-stream waits can emit nothing, so either (a) acquire with a short pre-stream TryAcquire+bounded wait and return true JSON 503 with retry_after (reusing the countdown for real), or (b) open the stream first and make the timeout an SSE `error` event with code CIRCUIT_OPEN plus explicit frontend handling for it. Option (a) is simpler and honestly reuses existing frontend code; it costs the `queued` position events (drop them — a 15s max wait doesn't need a position ticker). Do-nothing: implementer discovers the contradiction mid-build and improvises the contract ad hoc.
4. **[major] (confidence 7/10, Architecture review)** The error taxonomy has no row for client-initiated context cancellation, and the 'Timeout / mid-stream drop' row it is folded into records `circuit failure`. If client disconnects (tab close, navigation — routine user behavior) are classified via the timeout row, five users closing tabs opens the shared circuit breaker for everyone. The parenthetical '(partial text + failed run)' suggests the circuit is excluded, but the taxonomy — the plan's single classification point — never says so, and context.Canceled surfaces through the same error path as real timeouts in the current code (a.client.Do / scanner errors).
   - Plan quote: “the turn is then finalized exactly like a timeout (partial text + `failed` run)”
   - Recommendation: Add an explicit taxonomy row: `context.Canceled (client disconnect) → persist partial, mark run failed (or 'canceled'), NO circuit result recorded, no retry` — one errors.Is check at the classification point. Consider a distinct 'canceled' run status so telemetry can separate user aborts from provider failures. Do-nothing: acceptable only if the implementer happens to read the parenthetical the right way — too load-bearing to leave ambiguous in a plan whose whole §5.2 exists to make classification explicit.
5. **[major] (confidence 7/10, Architecture review)** The finalize gate and the degradation ladder conflict. §5.1 says under pressure the harness will 'skip the critic pass (critique stage falls back to single-context review with a visible notice)' and critic calls 'use TryAcquire and skip on contention'. If contention persists, the critic never completes a pass, and the gate's 'at least one critic pass completed' precondition can never be satisfied — finalize is deadlocked unless every user discovers the override. The plan does not say whether the degraded single-context review counts as a critic pass for gate purposes.
   - Plan quote: “`critique → finalize`: at least one critic pass completed (see 4.4) and no open `blocking` findings, or the user has explicitly overridden”
   - Recommendation: Specify it: when the critic is skipped by the degradation ladder, record a `critic-skipped: contention` marker that satisfies the gate but forces a `[CRITIC SKIPPED]` note into the finalize completeness report — degradation stays visible but never hostage-takes finalize (matching the plan's own 'caution must not become hostage-taking' principle). Alternative: have critic calls fall back to a normal (blocking) semaphore acquire when they are gate-critical. Do-nothing: leaves a load-dependent deadlock that only appears in production under contention — the worst time to discover it.
6. **[major] (confidence 7/10, Architecture review)** Idempotency semantics are unspecified for the common case: the duplicate arrives while the original run is still `running` (network blip = client lost the SSE stream, server is still streaming). There is no terminal state to return, the SSE stream cannot be replayed or re-attached, and the per-conversation TryLock would already answer 409 CONVERSATION_BUSY — making the idempotency key redundant for exactly the race it targets. The only case the key covers that the lock doesn't is a retry landing after the original finished, where 'return terminal state' as a plain JSON response to an endpoint whose success contract is text/event-stream is a new, undescribed response shape.
   - Plan quote: “a duplicate POST (retry after network blip) returns the original run's terminal state instead of double-running”
   - Recommendation: Either fully specify the state machine (running → 409 with original run id; terminal → JSON summary of the completed run + client refetches history, which the UI already does on reconnect) or defer idempotency wiring out of H4 entirely — the conversation lock plus the existing history-refetch-on-reconnect behavior already covers the practical failure, and the column loses nothing by staying dormant another release. My recommendation: defer; it's the weakest-value, highest-ambiguity item in the plan. Do-nothing (implement as written) risks an incoherent half-feature.
7. **[minor] (confidence 7/10, Architecture review)** The plan asserts 'No schema migrations required (ledger uses `meta`; everything else is code)', but sections_rev must be stored somewhere per-PRD and no such counter exists: prds has `current_revision` (the snapshot counter, wrong semantics — it doesn't bump on section saves) and `updated_at`. Either a new column is added (contradicting the no-migration claim) or the plan means compare-and-swap on prds.updated_at, which works with zero migration but is never stated.
   - Plan quote: “Add a `sections_rev` check: tool writes carry the rev they read; on mismatch the tool errors and the coach re-reads — the human always wins.”
   - Recommendation: State the mechanism: CAS on prds.updated_at (`UPDATE ... WHERE id=$1 AND updated_at=$2`) — no migration, no new concept, and 'rev' becomes the timestamp the tool read via get_prd. Tradeoff: timestamp equality is theoretically weaker than a counter under same-microsecond writes, which is unreachable given the per-conversation lock serializes the coach side. Do-nothing: implementer hits the contradiction and either silently adds a migration or silently drops the feature.
8. **[minor] (confidence 7/10, Architecture review)** Critic orchestration and findings persistence are unspecified. 'Run at critique-stage entry' — inside which lifecycle? If inside the advance_stage tool execution, a single tool call now contains a full second streaming LLM call (interacts with maxToolIterations, the idle watchdog, and SSE silence); if after the handler's runLoop, that is a new orchestration point in HandleMessage. Separately, the critique→finalize gate checks 'no open blocking findings' server-side, so critic findings must persist across turns — presumably in conversation meta alongside the ledger, but the plan never says where findings live, how they are marked resolved, or how round-2 'only re-examines previously-flagged sections' knows the flag set.
   - Plan quote: “One additional role, not a crew: a **fresh-context critic pass** run at critique-stage entry and after each revision round.”
