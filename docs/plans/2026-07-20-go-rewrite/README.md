## 1. Requirements Restated / 需求重述

1. **Backend & DB**: Rewrite the backend in Go. Drop Supabase; use PostgreSQL directly. Create an `insideout_app` role that holds all application permissions. Never write anything into the `public` schema. The `supabase-community` MCP is used for read-only reference against the live instance; the actual `insideout` database is a separate remote PostgreSQL instance the user provides, migrated by the Go server's own runner.
   **后端与数据库**：用 Go 重写后端。放弃 Supabase，直接使用 PostgreSQL。创建 `insideout_app` 角色承载所有应用权限。任何内容都不写入 `public` schema。`supabase-community` MCP 用于只读参考线上实例；真正的 `insideout` 数据库是用户提供的独立远程 PostgreSQL 实例，由 Go 服务自带的执行器迁移。
2. **Product**: Help users track projects developed/maintained by others (e.g., a group leader managing team progress). Fit collaborative/workshop settings. Let everyone record ideas; help refine ideas into PRDs; build agents that guide users toward better PRDs through interactive conversations, using LangChain's Go library.
   **产品**：帮助用户跟踪他人开发/维护的项目（例如组长管理团队进度）。适合协作/工作坊场景。让每个人都能记录想法；帮助把想法打磨成 PRD；构建通过交互式对话引导用户写出更好 PRD 的 Agent，使用 LangChain 的 Go 库。
3. **Frontend**: Prettify for a much more modern look and feel.
   **前端**：美化界面，呈现更现代的观感。

## 2. Where We Are Today / 现状摘要

The repo currently implements 卷了么 (JuanLeMe), a workshop companion app. Full findings are embedded in the companion docs; the load-bearing facts:
仓库当前实现的是「卷了么」工作坊伴学应用。完整调研结论见配套文档；关键事实如下：

- **DB**: everything lives in a custom `juanleme` schema, deeply Supabase-coupled: `auth.users` FKs, `auth.uid()` in every RLS policy, PostgREST roles (`anon`/`authenticated`/`service_role`), Vault for AI secrets. **Discovered during verification**: the repo's 7 migration files are a *stale subset* of the live database — on the live instance the RPC bridge was already moved out of `public` into `juanleme`, an `ai_run_events` telemetry table exists with no repo migration, live counts are 11 tables / ~22 functions, and the instance is **shared with unrelated projects**. The plan therefore baselines from the live schema, not the repo files, and never runs destructive migrations on the shared instance ([01 §1](01-database.md)). The rate limiter (10/min, 60/hr, advisory-lock serialized) and circuit breaker live in PostgreSQL functions — these are good and portable.
  **数据库**：所有对象都在自定义 `juanleme` schema，与 Supabase 深度耦合：`auth.users` 外键、每条 RLS 策略里的 `auth.uid()`、PostgREST 角色、Vault 存 AI 密钥。**核查中发现**：仓库里 7 个迁移文件只是线上数据库的*过期子集*——线上实例的 RPC 桥已从 `public` 移入 `juanleme`，存在无对应仓库迁移的 `ai_run_events` 遥测表，实际为 11 张表/约 22 个函数，且该实例**与无关项目共用**。因此本计划以线上 schema 而非仓库文件为基线，且绝不在共用实例上执行破坏性迁移（[01 §1](01-database.md)）。限流器（10/分钟、60/小时，advisory lock 串行化）和熔断器是 PostgreSQL 函数——质量好、可平移。
- **Backend**: two TypeScript Deno edge functions (`juanleme-ai-generate`: non-streaming Anthropic Messages API call with rate-limit/circuit checks; `juanleme-export-document`: synchronous markdown/print export uploaded to Supabase Storage).
  **后端**：两个 TypeScript Deno 边缘函数（`juanleme-ai-generate`：非流式调用 Anthropic Messages API，含限流/熔断检查；`juanleme-export-document`：同步生成 markdown/打印导出并上传 Supabase Storage）。
- **Frontend**: Nuxt 4 Universal SSR with a clean swappable service registry (5 interfaces, `mock` | `supabase` bundles) — a Go API client drops in as a third mode without touching pages/stores. But auth is half-fake (fabricated localStorage token), the 国风留白 / Ink & Seal token layer exists yet is **not wired in** (tokens.css never loaded, no component uses the semantic utilities), the homepage is still a HelloWorld showcase, and AI conversation history is localStorage-only.
  **前端**：Nuxt 4 Universal SSR，拥有干净的可切换服务注册表（5 个接口，`mock` | `supabase` 两套实现）——Go API 客户端可作为第三种模式接入，不动页面/store。但认证是半假的（伪造的 localStorage token），「国风留白 / Ink & Seal」令牌层虽存在却**未接线**（tokens.css 从未加载、无组件使用语义工具类），首页仍是 HelloWorld 展示页，AI 对话历史只存 localStorage。
- **No realtime; the UI's only Storage touchpoint is fetching the export's signed download URL**, which D8 eliminates — so the Go backend needs neither websockets nor an object-storage layer. Existing DB rows survive via dump/restore + schema rename (D1).
  **无 realtime；前端对 Storage 的唯一触点是获取导出的签名下载 URL**，D8 将其消除——因此 Go 后端无需 websocket 或对象存储。现有数据经转储/恢复 + schema 重命名（D1）保留。

## 4. Target Product Model / 目标产品模型

The three pillars and how they map to concepts (details in [03-agents.md](03-agents.md)):
三大支柱及其概念映射（详见 [03-agents.md](03-agents.md)）：

1. **Track others' projects / 跟踪他人的项目** — `workspace` (team, invite-code joined) contains `project`s, each with an owner, status, and a timeline of `project_update`s (progress / blocker / note). The group-leader view is a board of all projects with freshest updates surfaced.
   `workspace`（团队，邀请码加入）包含多个 `project`，每个项目有负责人、状态和 `project_update` 时间线（进度/阻塞/备注）。组长视图是项目看板，突出显示最新动态。
2. **Record ideas / 记录想法** — every member has a frictionless `idea` inbox per workspace (title + free text, quick capture). Ideas have a lifecycle: inbox → refining → converted (to PRD) / dropped.
   每个成员在工作区里有零门槛的 `idea` 收集箱（标题+自由文本，快速记录）。想法有生命周期：收集 → 打磨中 → 已转化（为 PRD）/ 已放弃。
3. **Refine into PRDs via agents / 通过 Agent 打磨成 PRD** — converting an idea opens a `prd` (structured sections, versioned via `prd_revision`) plus an `agent_conversation`. The PRD Coach agent interviews the user (clarify → draft → critique → finalize), writing PRD sections through tool calls. Review lifecycle: draft → reviewing (评审中) → approved (通过) / rejected — the design system already anticipated `PrdStatusBadge` for exactly this.
   将想法转化会创建 `prd`（结构化章节，经 `prd_revision` 版本化）和一个 `agent_conversation`。PRD 教练 Agent 采访用户（澄清 → 起草 → 批判 → 定稿），通过工具调用写入 PRD 章节。评审生命周期：草稿 → 评审中 → 通过 / 驳回——设计系统早已为此预留了 `PrdStatusBadge`。
