# 2026-07-26 — Nuxt dev server: IPv4 clients get a bare 426 (IPv6/IPv4 bind split)

## What was learned

A Nuxt 4 dev server can return a bare `HTTP/1.1 426 Upgrade Required` to
*every* ordinary HTTP request from IPv4 clients — including a browser —
while the app is actually up and serving fine over IPv6. The 426 has
`Content-Length: 16`, `text/plain` body `Upgrade Required`,
`Connection: keep-alive`, and crucially **no `Upgrade:` header**, so it is
not a real protocol-upgrade demand; it is an upgrade-only listener
answering a plain request. The cause is a two-socket bind: with no `HOST`
set, the Nitro/Vite dev server binds the app to IPv6 `[::1]` and a
*separate* IPv4 `*:port` socket that exists only for HMR/WebSocket
upgrades. Any client that reaches the IPv4 socket gets the bare 426.

On this macOS box `localhost` resolves to IPv4 first, so `curl localhost`
and a browser navigation to `http://localhost:PORT` both hit the 426
socket, while `http://[::1]:PORT` returns 200 with `x-powered-by: Nuxt`.

## Evidence (controlled experiments, 2026-07-26)

Stack at the time: Nuxt 4.4.8, Vite 7.3.5, Nitro 2.13.4, Node v25.6.0.

- A bare `node` HTTP server on the same high port returned **200** to the
  same IPv4 client that got 426 from `nuxt dev` — so the network/proxy
  stack was not at fault.
- `lsof` of the `nuxt dev` process showed **two** listeners on the port:
  an IPv6 `[::1]` socket and an IPv4 `*:port` socket.
- Direct probe: `curl http://127.0.0.1:PORT` → 426 (no `Upgrade:` header);
  `curl http://[::1]:PORT` → 200, `<title>InsideOut</title>`,
  `x-powered-by: Nuxt`.
- Hypotheses eliminated before landing here: an HTTP proxy
  (`--noproxy '*'` was byte-identical; `NO_PROXY` already held 127.0.0.1),
  the `@nuxt/cli` dev-lock / a second instance, and HTTP/2
  (`--http2-prior-knowledge` → connection refused).

## The wrong first hypothesis

The initial guess was "Node v25.6.0 is unsupported — re-run on a Node LTS
(20/22)." That was **false** and should not be repeated: every `node@NN`
binary on this machine (`node@19/22/23/25`) is actually v25.6.0, so a
version swap was never available to test, and the bare-node 200 above
shows the Node version is irrelevant anyway. The bug is the bind topology,
not the runtime version.

## Scope

- Affects the **dev server only** (`nuxt dev` / `nuxi dev`). A production
  build (`nuxt build` + `node .output/server/index.mjs`) listens on a
  single socket and does not show the split.
- Reproduced on macOS where `localhost`/the default route prefers IPv4.
  Hosts where the default dev bind already serves IPv4 may not see it.
- It interacts badly with this project's **host-only cookie** rule: those
  cookies force you to use one hostname consistently, and the natural
  choice is `127.0.0.1` — which is exactly the IPv4 socket that 426s
  without `HOST`. So the trap is self-reinforcing here: the security
  posture that wants `127.0.0.1` is the posture that trips the 426.

## When to apply it again

Reach for this when a Nuxt/Nitro **dev** server returns a blanket
`426 Upgrade Required` with **no** `Upgrade:` header to curl and the
browser alike, while the backend (or a bare node server) on the same
machine answers normally. Before suspecting the Node version or a proxy:

1. `lsof -nP -iTCP:<port> -sTCP:LISTEN` — look for two listeners (an IPv6
   `[::1]` and an IPv4 `*:port`).
2. Probe each family: `curl -i http://127.0.0.1:<port>` vs
   `curl -i http://[::1]:<port>`. If only the IPv6 one returns the app,
   this is the bind split.
3. Fix by binding one family: run the dev server with
   `HOST=127.0.0.1` (a single IPv4 socket then serves the app), or reach
   it via `http://[::1]:<port>`. The first is preferable here because it
   matches the host-only-cookie hostname.

Pair this with the random-high-port habit (use an unusual high port for a dev
server rather than 3000/8080, so a stale process on the conventional port
cannot be mistaken for yours): keep the app's `NUXT_API_INTERNAL_BASE` proxy
port and the backend port in sync — `./scripts/env.sh propagate` is what keeps
the generated `app/.env` agreeing with the root after you move one
([environment.md](../usage/environment.md#frontend)) — and now also pin `HOST`
so the chosen family is the one the app actually serves on.
