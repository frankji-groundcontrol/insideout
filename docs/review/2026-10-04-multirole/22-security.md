# 22 · Security

**Lens:** authentication coverage on every route, session/token design, CORS, cookies, RLS workspace isolation, webhook HMAC, config/secret handling, container posture, env-tooling injection surface
**Score:** **7.0 / 10**
**Bottom line:** The security core of this repo is unusually disciplined for its size: every data route is behind `requireAuth`/`requireAdmin`, refresh tokens are hashed at rest with atomic rotation and replay detection, the GitHub webhook verifies HMAC in constant time and fails closed at 503 when unconfigured, RLS is forced on every domain table, signup fails closed to invitation-only, and the JWT secret has a boot-time floor. No secret has ever been committed — git history shows only `.env.example` files ever tracked. The real hole is what is missing: zero rate limiting or lockout on the credential-verifying auth endpoints (login is brute-forceable at unlimited speed, and the email-token request endpoints can bomb a victim's inbox while burning their live tokens), plus a root-running container with no healthcheck and an RLS backstop whose NULL-context trust is enforced only by code-review convention.

Reviewed against main@877ad03; High/Critical findings re-checked by an independent skeptic — verdicts in 01-findings-register.md.

## Scope

I read every route registration in `server/internal/api/` and traced each handler's auth gate; `server/internal/auth/` (JWT, refresh, one-time tokens, password hashing); `server/internal/store/` (pool, users, sessions, auth tokens, invitations) and all 26 migrations in `server/db/migrations/` plus `provision_roles.sql`; the webhook handler and `server/internal/github/` (HMAC verify, App auth, guide fetch); `server/internal/config/config.go`; `cmd/insideout/main.go`; the MCP server and CLI auth surfaces; `docker-compose.yml`; `server/Dockerfile`; `.env.example`; and the env tooling in `scripts/` (`env.sh`, `env-write.sh`, `env-lib.sh`, `dev.sh`). I verified git history for any committed `.env` and ran a repo-wide search for rate-limit/throttle machinery. I did not read any `.env` file or secret value.

## What is good

- **Complete auth coverage, verified route by route.** Every data route in `server/internal/api/` wraps its handler in `requireAuth` or `requireAdmin` (e.g. `projects.go:14-21`, `admin.go:22-26`). The only unauthenticated routes are `/healthz`, the eleven `/api/v1/auth/*` endpoints, and `POST /api/v1/hooks/github` — which is authenticated by HMAC instead of session, deliberately (`github_webhook.go:20-22`).
- **Webhook done right.** Signature is checked first, always, in constant time (`webhook.go:14-26` uses `hmac.Equal`), the body is capped at 8 MiB, unknown events are acked and ignored, and an unconfigured secret returns 503 (`github_webhook.go:32-34`) — a fail-closed posture.
- **Refresh-token lifecycle.** 256-bit opaque tokens, sha256 digest at rest (`refresh.go:14-25`), rotation via affected-rows conflict so a replayed token clears cookies and dies (`auth.go:200-216`), and password reset revokes every live session (`auth_email_flows.go:172`).
- **Password and code discipline.** argon2id at 64 MiB with constant-time compare and a bcrypt upgrade path (`password.go:19-24,95-97`); 6-digit login codes get a 5-attempt budget that retires the code (`auth_tokens.go:80-102`), and the request endpoints answer a uniform 200 to prevent enumeration.
- **Defense in depth at the database.** 17 tables have `ENABLE/FORCE ROW LEVEL SECURITY` across migrations, consistently keyed to `_is_member`/`_is_admin` helpers; `provision_roles.sql` splits `insideout_owner` (DDL, BYPASSRLS) from `insideout_app` (runtime, NOBYPASSRLS); signup mode seeds `invitation_only` and fails closed on malformed settings (`invitations.go:42-48`).
- **Hardened server defaults.** JWT HS256 with an algorithm allow-list check and a 32-char secret floor enforced at boot (`jwt.go:40-45`, `config.go:98-100`); cookies Secure-by-default, HttpOnly, SameSite=Lax, refresh cookie path-scoped to `/api/v1/auth` (`cookies.go:19-38`); read/header/idle timeouts plus a 1 MiB body cap (`main.go:144-154`, `middleware.go:92-103`). No SSRF: repo URLs are re-parsed into owner/repo and fetches go to a fixed `api.github.com` base (`github.go:98-110`).
- **Careful env tooling.** Values are never printed (masked by length), `propagate` refuses git-visible destinations and clobbers, writes are `chmod 600`, and value splices go through awk/`ENVIRON` rather than sed/eval (`env-write.sh:57-64,94-114`, `env-lib.sh:124-160`).

## Findings

**SEC-01 · High · auth rate limiting — no throttle or lockout on credential-verifying endpoints.** `server/internal/api/auth.go:153` — `ok, err := auth.VerifyPassword(user.PasswordHash, req.Password)` followed by a bare 401 on mismatch (line 155): there is no attempt counter, delay, or 429 path anywhere in the auth surface. The only limiter in the repository is the AI coach's (`20260720135755_ai_ops.sql:26`: `CREATE OR REPLACE FUNCTION insideout.ai_check_rate_limit(p_user_id uuid)`), which no auth route calls; password policy is just `len(req.Password) < 8` (`auth.go:63`). *Failure scenario:* an attacker who learns a member's email (invitation-only signup protects account creation, not existing accounts) runs a dictionary/credential-stuffing attack against `POST /api/v1/auth/login` at unlimited speed — each miss still costs a 64 MiB argon2id verify, so the same endpoint doubles as a CPU-exhaustion DoS. *Fix:* add a small per-IP + per-account token-bucket middleware mounted on `/api/v1/auth/*` (e.g. `golang.org/x/time/rate`, 10/min/IP, 5/min/account) returning 429 with `Retry-After`, preserving the uniform-401 contract. *diff_size: ~100 lines.*

**SEC-02 · Medium · email-token request endpoints enable mailbox-bombing and live-token invalidation.** `server/internal/api/auth_email_flows.go:36-38` — `handleMagicLinkRequest` looks the user up and sends with no cooldown (identical shape at `:101` forgot-password and `:185` login-code); every send first runs `server/internal/store/auth_tokens.go:33-34`: `DELETE FROM insideout.auth_tokens WHERE user_id = $1 AND kind = $2 AND used_at IS NULL`. *Failure scenario:* an attacker POSTs `{"email":"victim@corp"}` in a loop — the victim's inbox is flooded (burning Resend quota/money), and any link or code they were about to click is destroyed by each request. *Fix:* enforce a per-email + per-IP send cooldown (e.g. one per 60 s) before `send`, still answering the uniform 200. *diff_size: ~30 lines.*

**SEC-03 · Medium · container runs as root with no healthcheck (L8).** `server/Dockerfile:8-11` — `FROM gcr.io/distroless/static-debian12` then `COPY` + `ENTRYPOINT ["/insideout"]` with no `USER` directive, so the process runs as uid 0; there is no `HEALTHCHECK` in the image, and the compose server service (`docker-compose.yml:30-54`) has none either — only postgres does (`:24-28`). *Failure scenario:* any RCE or container-escape primitive lands as root, and an orchestrator cannot detect a wedged server process (the SSE coach stream means no WriteTimeout by design, so a stuck stream is invisible without a probe). *Fix:* add `USER nonroot:nonroot` (distroless uid/gid 65532) and a healthcheck — a tiny Go `health` subcommand, since distroless has no shell/curl. *diff_size: ~6 lines.*

**SEC-04 · Medium · RLS NULL-context trust is convention-enforced and untested.** `server/db/migrations/20260720150000_row_level_security.sql:33` — the users policy begins `insideout.current_user_id() IS NULL OR ...`, treating an unset session variable as trusted system context; `server/internal/store/pool.go:102-105` states "Every store function touching an RLS-protected table must go through this" — but nothing checks it. `authz_test.go` exercises membership rules, not the unset-context boundary. *Failure scenario:* a future one-line store helper that queries `users` or `projects` without `withUserContext` (or a new table created without `FORCE ROW LEVEL SECURITY`) silently disables workspace isolation at the DB layer, and review is the only gate. *Fix:* add a DATABASE_URL-gated integration test that, for every RLS table, asserts zero rows for a non-member actor and a defined-deny result for the unset context. *diff_size: ~100 lines test.*

**SEC-05 · Low · CORS middleware sets `Vary: Origin` only for allowed origins.** `server/internal/api/cors.go:60-62` — `w.Header().Set("Vary", "Origin")` sits inside `if originAllowed(origin, s.cfg.CORSOrigins)`; denied-origin responses carry no `Vary`. *Failure scenario:* an intervening shared cache can serve the ACAO-carrying response to a disallowed origin, or cache the denial for an allowed one. *Fix:* set `Vary: Origin` unconditionally whenever the CORS middleware is mounted. *diff_size: 1 line.*

**SEC-06 · Low · `INSIDEOUT_DEV_CORS=1` reflect-any-origin is a production footgun one env var away.** `server/internal/api/middleware.go:128-129` — `w.Header().Set("Access-Control-Allow-Origin", r.Header.Get("Origin"))` with `Access-Control-Allow-Credentials: true`, gated only by `config.go:88` (`c.DevPermissiveCORS = os.Getenv("INSIDEOUT_DEV_CORS") == "1"`), and `.env.example:88-91` documents the knob next to the production vars. *Failure scenario:* an operator copies a dev `.env` to the hosted deployment, and any website can make credentialed cross-origin requests and read the responses — full session compromise, since the JSON body also carries the access token. *Fix:* refuse to start (or log at Error) when DevPermissiveCORS is set alongside a non-local `INSIDEOUT_PUBLIC_URL`. *diff_size: ~5 lines.*

**SEC-07 · Low · bundled postgres ships a documented default superuser password on all interfaces.** `docker-compose.yml:13` — `POSTGRES_PASSWORD: ${POSTGRES_SUPERUSER_PASSWORD:-insideout_dev_password}` with `ports: - "${POSTGRES_PORT:-5442}:5432"` (`:20`), binding 0.0.0.0. *Failure scenario:* a dev laptop on an untrusted LAN runs compose and the cluster superuser is reachable with the password printed in the repo. *Fix:* drop the `:-default` (require the variable) and bind `127.0.0.1:${POSTGRES_PORT:-5442}:5432`. *diff_size: 2 lines.*

**SEC-08 · Low · tracked docs expose deployment identifiers and a durable test account (L11).** `README.md:64` — `托管站点 / hosted: ` + the Railway app URL (redacted: `https://<railway-host>`); `docs/changelogs/2026-08-21-dogfood-and-cleanup.md:8` — "Durable account `dogfood@<prod-domain>` (credentials in the" — and the production domain appears across `docs/HANDOFF.md` and five changelogs. This violates the AGENTS.md redaction rule. *Failure scenario:* anyone with repo read access gets the prod hostname, custom domain, and a known live account to target. *Fix:* replace with `<railway-host>` / `<prod-domain>` / `<email>` placeholders per the convention. *diff_size: ~10 lines across files.*

**SEC-09 · Low · stale secret file from the deleted Nuxt app sits unrecorded in the worktree (L10).** `app/.env` — `ls -la app/` shows `-rw------- ... 479 Jul 30 10:29 .env`: a two-month-old secret file in a directory removed from git on 2026-08-18. History confirms no real `.env` was ever tracked (only `app/.env.example`), so nothing needs rotating — but AGENTS.md asks for untracked secret-bearing files to be recorded in a local manifest, and this one is neither recorded nor deleted. *Failure scenario:* a forgotten credential file nothing reads persists on disk indefinitely, invisible because gitignored. *Fix:* delete `app/.env` (its app is gone); if anything still consumes it, record it in the untracked-file manifest. *diff_size: 1 file.*

## Recommendations

1. Land per-IP + per-account rate limiting on `/api/v1/auth/*` before the hosted instance gains users (SEC-01) — it is the only finding here an unauthenticated stranger can exploit today.
2. Add send-cooldowns to the magic-link, forgot-password, and login-code request endpoints (SEC-02).
3. Harden the container: `USER nonroot` in the Dockerfile plus a healthcheck path for the compose/Railway service (SEC-03).
4. Write the DATABASE_URL-gated RLS regression test that walks every RLS table with a non-member actor and the unset context (SEC-04).
5. Delete `app/.env` and start the local untracked-file manifest AGENTS.md requires (SEC-09).
6. Redact the Railway host, prod domain, and dogfood account from tracked docs (SEC-08).
7. Always emit `Vary: Origin` from the CORS middleware, and gate `INSIDEOUT_DEV_CORS` behind an explicit environment check with a loud startup warning (SEC-05, SEC-06).
8. Remove the postgres default superuser password and bind the mapped port to 127.0.0.1 (SEC-07).

## What this role would do first

Rotate nothing — history is clean — but treat the deployed instance as the exposure to fix: nothing committed needs rotation today (no `.env` ever reached git; secrets live only in Railway's environment and in two local files, root `.env` and the stale `app/.env`). What must not be exposed past localhost until SEC-01 and SEC-02 land is the hosted API itself on `<prod-domain>` and `<railway-host>`: it presently lets any stranger hammer `POST /api/v1/auth/login` and the three email-request endpoints without a single 429. Locally, keep `INSIDEOUT_DEV_CORS=1`, the compose-mapped postgres (default superuser password), and a bare `go run` server on `:8080` bound to interfaces beyond the loopback — each is one mistake away from becoming a real exposure.
