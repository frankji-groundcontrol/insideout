## Responsive/Overflow Reviewer

### What I examined

I read the app chrome (`client/lib/app.dart`, `client/lib/chrome/product_dock.dart`), every page-level layout file (`dashboard_page.dart`, `workspace_page.dart`, `project_page.dart`, `ideas_page.dart`, `prd_page.dart`, `roadmap_page.dart`, `versions_stack.dart`, `versions_commit_dialog.dart`, `coach_panel.dart`, `field_card.dart`), the web host file (`client/web/index.html`, `client/lib/main.dart`), the local Flutter 3.44.8 SDK sources for `Scaffold` and `RenderPositionedBox` layout behavior, the pre-built code map, and the capture index. I personally inspected shots 04, 06, 09, 11, 16, 19, 20, and 21 at full resolution; the remaining desktop shots are corroborated by the capture index (A2). Mobile coverage at 390px exists only for dashboard (19), ideas wall (20), and the resize anomaly (21) — a gap I flag as a finding in itself.

### The confirmed defect, with its real root cause

The lead-confirmed defect — "at 1440x900 the bottom dock overlays dashboard body content" — is real but misdiagnosed by its symptom. The dock does not sit at the bottom at all. In shot 04 the pill is centered at approximately (720, 440) of a 1440x900 viewport; in the narrow shots 19/20 it is centered at approximately (390, 825) of 780x1688 — in both cases the vertical midpoint of the screen, with a large empty band below. Shot 21 shows the same mid-screen placement after resize.

The cause is a three-part chain. `AppScaffold` passes the dock as `bottomNavigationBar: signedIn ? const ProductDock() : null` (`client/lib/app.dart:135`) on a `Scaffold` with `extendBody: true` (`app.dart:71`). `ProductDock.build` returns `SafeArea(minimum: EdgeInsets.fromLTRB(16, 0, 16, 16), child: Center(child: Material(...)))` (`client/lib/chrome/product_dock.dart:26-28`). The Scaffold's own layout delegate (`scaffold.dart:1035,1049-1052` in the SDK) lays out the bottomNavigationBar with `fullWidthConstraints` — width tightened to the viewport, height bounded to it. `Center` is `Align` with no factors, and `RenderPositionedBox.performLayout` only shrink-wraps when `constraints.maxHeight == double.infinity`; here it is finite, so the `Center` expands to the full 900px and vertically centers the pill inside it. The 900px-tall bottomNavigationBar is then positioned at `bottom - height = 0`, so the pill lands at the viewport's vertical center on every signed-in route. The correct minimal fix is `Align(alignment: Alignment.bottomCenter, heightFactor: 1.0)` — the `heightFactor` restores shrink-wrap — after which the pill truly anchors at the bottom and every page's `bottom: 140` padding starts meaning what it was written to mean.

### Strengths worth keeping

The code underneath the bug is more disciplined than the rendering suggests. There is a single breakpoint convention — `MediaQuery.sizeOf(context).width >= 900` at `dashboard_page.dart:134`, `prd_page.dart:153`, `assembly_step.dart:33` — and narrow branches genuinely exist (dashboard cards stack at `dashboard_page.dart:171-175`; the PRD split becomes a stacked ListView at `prd_page.dart:165-169`). Button groups on the project page use `Wrap` (`project_page.dart:162-180`), which cannot overflow horizontally. The ideas-wall grid math at `ideas_page.dart:239` — `(width - 88) / 3`, `(width - 72) / 2`, `width - 56` — is exactly self-consistent with its ListView's 56px horizontal padding at both breakpoints. `FieldCard` clips (`field_card.dart:31`), which safely contains the idea poster's deliberately off-edge decorative circle (`ideas_page.dart:292-302`). `SafeArea` is used for the dock, the top-right utilities, and the auth modal, and the display type is fluid via a clamp (`cobalt.dart:97`).

### Findings walkthrough (severity order)

Beyond re-rooting the dock defect, the High items are latent or host-level. The coach panel (`coach_panel.dart:129`, bottom padding 8) and the roadmap canvas view (`roadmap_page.dart:176` header bottom 8, canvas `Expanded` with no clearance) are the only full-height surfaces with no dock clearance; today this is masked by the floating dock, but once the pill is bottom-anchored the coach's input row and the canvas bottom will sit under it — these must land in the same change set as the dock fix. Separately, `client/web/index.html` has no `<meta name="viewport">` at all — only description and apple meta tags — so on a real phone the page renders at the browser's ~980px fallback width; the 390px shots look correct only because CDP emulation forces device metrics. This also plausibly contributes to the resize gutter in shot 21, where shrinking the window post-boot leaves a stuck ~245px canvas column with a white band, unrecovered by dispatched resize events.

Medium findings: the top-right utility `Row` (`app.dart:90-97`) is a `Positioned` `mainAxisSize: min` with no width budget — fine for the bare four icons (~180px), but the roadmap page injects a three-segment `SegmentedButton` as actions and no narrow roadmap shot exists to prove it survives 390px. `versions_commit_dialog.dart:52` hardcodes `width: 420` inside an AlertDialog whose default insets leave ~310px at 390px — a guaranteed horizontal overflow at the single most important first-run action (first commit). `versions_stack.dart:62` pins the commit stack to `height: 580` with an unbounded readiness-gap `Column` inside — a long gap list overflows with no scroll, and the fixed block dominates short windows. `prd_page.dart:167-168` fixes narrow-layout desk/coach heights at 640/520 regardless of content or viewport. Low findings: the dead `static const height = 88.0` (`product_dock.dart:15`, zero references) versus six independently hardcoded `bottom: 140` paddings; the painted title's 88px right reservation against a ~180-460px utility row (`app.dart:80`); the missing narrow captures for ten of thirteen routes; and the fixed 240px side panes in the roadmap band/progress views that consume 72% of a 390px column.

### What I would do first

Swap `Center` for `Align(alignment: Alignment.bottomCenter, heightFactor: 1.0)` in `ProductDock.build` — one line — and immediately re-shoot pages 04, 06, 09, 11, 16, 19, and 20. That single change converts every "overlapping dock" symptom from a mystery into a measurable bottom-clearance question, at which point findings 2, 9, and 10 become a small, well-defined cleanup rather than a forensic exercise. The viewport meta tag should land in the same hour; everything else can follow the re-shoot evidence.
